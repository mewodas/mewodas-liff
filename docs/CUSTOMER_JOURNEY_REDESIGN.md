# FitMeal 顧客動線リデザイン設計書

**起案日**: 2026-05-28
**ステータス**: 設計ドラフト（社長レビュー待ち）
**前提**: LINE不要デモモード（read-onlyトークン機構）実装済み（staging `4a66a17`）。本設計はその機構を土台に置き場所と入口を作り変える。

## 背景と狙い

公開単独ページ `/demo` だけでは「ジム自身が自分の管理画面の中で顧客UIを体感する」体験が弱い。新規ジムがログインした瞬間に "中身の入った状態" を見せ、「あ、こういうUIね」を即理解させたい。あわせてジムが自分の顧客を入れていく動線を明快にし、エンドユーザー体験のUI/UXを底上げする。

## 確定方針（2026-05-28 社長決定）

1. **公開 `/demo` は残す**（LP・不特定多数向け）。**かつストア内プレビューも作る**（両方）。
2. **新規ジムのテナントにサンプル顧客1名を自動シード**（申込時）。ラベル明示・課金席数から除外・1クリック削除可。
3. **ストアに「実データプレビュー」も入れる**（オーナーが実在顧客の画面を読み取り専用で確認）。

## 全体フロー（リデザイン後）

```
【第1層：ジムの申込〜利用開始】
 申込（LP/フォーム）→ Stripe Checkout（14日trial）→ webhook → provisionTenant()
   └─ ★同時に「サンプル顧客1名＋直近7日分の食事・体重」を自テナントへシード
        ・isSample 明示／課金席数カウント外／削除可
 ウェルカムメール → /store ログイン
   └─ 顧客リストにサンプル1名が見える＝空っぽスタートを回避
        └─「顧客画面プレビュー」→ そのサンプルのエンドユーザー画面(/home等)を読み取り専用で体験

【ストア内「顧客画面プレビュー」（モード切替）】★新
 ・サンプルモード … シードしたサンプル顧客で体験
 ・実データモード … 実在顧客を選んで読み取り専用プレビュー（オーナー認証で発行する preview トークン）

【第2層：ジムが自分の顧客を入れる】
 (a) 招待URL（/home/register?t=署名トークン, 7日）を顧客へ共有  または
 (b) 申込フォームに回答 → アカウント自動作成
   → 顧客側ログインURL(LIFF)を確認 → 共有 or リッチメニューに埋め込む → 利用開始
 → サンプル顧客は不要になれば削除

【公開デモ（既存・維持）】
 LP「顧客画面デモを見る」→ /demo → /api/public/demo/start → /home（共有デモ顧客）
```

## コンポーネント別仕様

### 1. サンプル顧客の自動シード（`lib/provisionTenant.ts` 拡張）
- テナント作成成功後、当該テナントの顧客DB/食事DB/体重DBへサンプルを投入する共有関数 `seedSampleCustomer(tenantId, dbIds)` を追加。
- 投入内容: サンプル顧客1名（例「山田 花子」相当・進行中・目標kcal/PFC・身長体重）＋ シード実行日基準で直近7日分の食事（朝昼夕＋一部間食）＋ 体重（緩やかな減少トレンド）。日付はシード実行日を基準に動的生成。
- **サンプル識別**: 顧客レコードに `isSample` 相当のマーカーを持たせる（Notion チェックボックス列 追加 or lineUserId を固定接頭辞 `SAMPLE_` にする）。lineUserId はテナント内ユニーク（各テナント専用DBなので固定値で可）。
- **課金除外**: 席数カウント（seat/billing）でサンプルを除外する。`isSample` のレコードはアクティブ席数に数えない。該当ロジック（lib/ の seat 集計 / billing/info）に除外条件を追加。
- **冪等性**: provisionTenant 自体が冪等。シードも「サンプルが既に存在すれば skip」で二重投入を防ぐ。
- **削除**: 既存の顧客削除フローで消せる。加えて「サンプルを削除」導線を顧客一覧に用意（任意）。

### 2. ストア「顧客画面プレビュー」（新規 UI）
- 入口: `/store/customers`（=/admin/customers）の各顧客行＋サンプル行に「顧客画面を見る」ボタン。または `/store` ダッシュボードに「顧客画面プレビュー」セクション。
- モード切替: **サンプル / 実データ**。実データは顧客セレクタで対象を選ぶ。
- レンダリング方式: 顧客アプリ（/home 等）を**iframe で埋め込み**、プレビュートークンを **URLクエリ（`?preview_token=...`）で渡す**。
  - ⚠️ localStorage はオリジン共有のため、デモと同じ `fitmeal_demo_token` を localStorage に入れるとオーナーのストアセッションへ漏れる。**プレビューは localStorage を使わず URLパラメータ + sessionStorage（iframe内ページ単位）で受け渡し**、メインのストア画面と隔離する。`lib/demoClient.ts` を「localStorage または URL/sessionStorage のトークン」を見るよう拡張。

### 3. 実データプレビュー用トークン（`lib/demoSession.ts` 拡張 + admin エンドポイント）
- demoSession を `kind: 'demo' | 'preview'` 対応に拡張（署名形式・read-only強制は共通）。
- 発行: 新規 `POST /api/admin/preview-token`（`withAdminTenant` 認証必須）。body の customerId/lineUserId が**現在の認証テナントに属する顧客であることをサーバーで検証**し、`{ tenantId: 現在テナント, lineUserId, kind:'preview', exp:短め(例60分) }` の署名トークンを返す。
  - 🔒 セキュリティ要点: tenantId は**入力ではなく認証セッションから**取る。オーナーは自テナントの顧客しかプレビューできない。
- 検証: `withLiffTenant` の既存デモ分岐を `verifyDemoToken`（demo/preview両対応）に拡張。`kind` を問わず **非GETは403**・テナントはトークン内固定。
- 公開デモトークン（kind:'demo'・長期）と実データプレビュートークン（kind:'preview'・短期・オーナー発行）を区別。

### 4. 公開 `/demo`（既存・維持）
- `app/demo/page.tsx` + `/api/public/demo/start` はそのまま。共有デモ顧客を参照（本番反映には Production env + 本番デモ顧客が必要＝既知TODO）。

### 5. 第2層オンボ導線の UI 明確化（既存機能の見せ方改善）
- `/store/customers` の「ユーザー招待フォームをコピー」を、3経路が分かるUIに整理:
  1. 招待URLを共有（既存・/home/register?t=）
  2. 顧客側ログインURL（LIFF）を確認 → 共有 or リッチメニュー埋め込み（手順リンク）
  3. （承認制は将来）
- 「顧客にはこう見えます」プレビューへの導線をオンボチェックリストに追加。

## エンドユーザー UI/UX 改善（並行トラック・原則）
全面改修は別工数だが、本リデザインで効く改善を優先:
- **初回ストア体験**: 空状態を廃し、サンプル＋ガイド付きチェックリスト（LINE連携→顧客招待→プレビュー）。
- **「顧客にはこう見える」を常時1クリック**で（営業・自己確認の両用）。
- **招待〜利用開始の手順を1画面に集約**（URL共有／リッチメニュー埋め込み手順）。
- エンドユーザー側（/home 等）の改善要望は別途バックログ（[[project_liff_deferred_tasks]] と統合）。

## 課金・セキュリティ・データ整合
- サンプル顧客は席数・課金から除外（重要：誤課金防止）。
- preview トークンは admin 認証必須・自テナント限定・read-only・短期。
- demo トークンは公開・read-only・共有デモ顧客限定。
- lineUserId はテナント内ユニーク厳守（重複すると食事一覧0件バグ。[[feedback_test_customer_line_id]]）。

## 実装フェーズ案
- **Phase A**: サンプル顧客シード（provisionTenant）＋席数除外＋ストア「顧客画面プレビュー（サンプルモード）」（iframe + URLトークン）。既存デモ機構の再利用が中心。
- **Phase B**: 実データプレビュー（preview-token 発行 + 顧客セレクタ + モード切替）。
- **Phase C**: 第2層オンボ導線UI整理＋初回チェックリスト＋UX改善。
- 公開 `/demo` は既存のまま維持。
- 全て顧客側ファイルに触れるため **staging必須＋fitmeal-qa→社長確認→main**（[[feedback_staging_required]] [[feedback_qa_before_owner]]）。
